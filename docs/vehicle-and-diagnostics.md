## 1. 空调同步、验证与目标状态

### 1.1 车控分组刷新与快照缓存（当前）

- `VehicleController` 按风量、空调状态、设定温度、舒适功能和环境传感器分组读取；`VehicleRefreshQueue` 统一安排期限与合并请求，所有厂商分组读取继续使用既有单条 HAL I/O 队列，不为每个通道创建线程，也不默认开启未验证的 watcher。
- 风量组包含手动和 AUTO 风量；空调状态组包含 AC、循环、风向和双温同步；舒适组包含四路座椅通风/加热、前后挡和方向盘加热。点火、舱温、外温归传感器组；点火沿用 2500ms 基准，实际更新仍受单队列排队和读取耗时影响。
- 各组完成后的最短轮询间隔：风量 500ms，空调状态 1000ms，设定温度、舒适功能和传感器 2500ms。座椅长按弹窗打开即请求一次舒适组读取，可见期间舒适组按 500ms 兜底，关闭后恢复常态。Dock 每 250ms 只检查调度期限；正在执行的慢 IPC 不能被抢占，因此这些数字不是车机显示延迟上限。
- 当前连接已接受订阅且实际见到完整合法事件后，可降低兜底读取：风量配置两路并有任一路等级事件时 2500ms，AC/循环/风向/双温同步四项均有事件时 2500ms，主副驾温度均有事件时 5000ms。没有事件而数值未变化不判故障；任意只读回发现新值、订阅失败或连接变化会保守恢复原快速周期，写后定向确认不等待慢周期，点火和舒适组不降频。
- 每组最多保留一个待执行请求；执行中的显式刷新只合并保留一次后续读取。轮转取组避免高频风量请求饿死其它组。媒体和音量保留独立的 2500ms 后台刷新，不在车控分组里读取，也不因调度 tick 强制重绑整栏。
- 本地操作的 900ms 写后刷新只包含受影响分组；不同组的请求合并保留，不再每次读取全部通道。风量目标最多覆盖显示 1500ms，其它属性目标 3500ms；真实回调和回读始终保存到 observed，不再因为与目标不同而丢弃。匹配观测确认目标，过期或失效后回落最近观测；原权限、门禁和熔断保持。
- 分组结果回主线程后只合并真实观测，按精确采样属性确认对应目标；回调和用户意图推进分组修订号。旧读取不能覆盖较新的同组事件或操作，同值有效事件也会使旧读取失效，但相同显示不重复通知。读取结果发布不推进意图修订号，避免较早轮询废弃稍后执行的最终温度回读。
- 读取优先配置 zone 或本连接命中的读区缓存，备用只在明确同功能区域内尝试；温度和座椅不跨主副驾。缓存失效或连接变化后重新按配置读取，读命中绝不自动保存为控制区域。周期备用探测最短2500ms，显式刷新可重新探测；日志分别记录配置zone和实际读zone。
- `CabinVolume` 缓存最近一次真实媒体音量观测，用写入代际拒绝写前或写中启动的旧读取覆盖写后缓存。后台读取和写后回读仅在数值改变时通知既有监听；`DockSnapshots.capture()` 复用缓存，冷启动尚无观测时允许一次真实读取。独立编辑预览在每次显式 `render()` 开始时采样一次音量，整批条目共用一份快照，不依赖 Dock 服务轮询，也不在绘制或逐条目绑定时重复读取。`DockOverlayService` 对相同快照跳过重绑，重挂载会清除旧快照缓存。
- 提高风量和空调组采样频率会增加这两组的基础读取次数，不能据此声称总 IPC、CPU 或功耗一定下降。具体收益须依据日志中的分组 `wait` / `io` 耗时和真车回归判断；本机验证不能代替厂商接口及真实车辆效果验证。

### 1.2 原车车控接口按需验证（当前）

- “诊断与日志”提供“车控接口验证（2分钟）”“停止车控接口验证”“查看车控验证结果”；默认选择风量，另可验证常用空调、温度和座椅。副驾通风、前后挡除霜、方向盘加热可分别做只读订阅验证：只临时加入选中的一路，验证任务只额外调度舒适组，不触发传感器组的自动座椅逻辑，不修改日常选择或写入策略。验证不自动写车控、不补权、不修改用户写入开关及安全等级；额外浮点读取仍由用户显式选择温度模式开启。
- 「急速降温：原厂 MAX A/C」只临时加入 `ac_max` 的事件和空调组整数轮询，不加入日常配置。停车后先用原车界面开关，确认全局区 `0x80000000`、功能号 `0x10010400` 的事件或读回随 `0/1` 变化。保持原车 MAX A/C 关闭，在验证窗口内打开 Dock 主驾温度弹窗，点击「MAX 试开」。也可在「诊断与日志 → 急速降温测试写入」显式试开或试关。两个入口共用现有写门禁和后台队列，只发裸值 `1/0`，不另写温度或风量。试写窗口失效后，已打开的试写按钮不会退回组合写；非验证期间新打开的 Dock MAX 仍是原组合预设。
- `HVAC_TEST AC_MAX_WRITE` 区分请求来源、未提交/未执行、实际调用返回；报告并列展示最近实际调用及其 `OBSERVED_MATCH`／`OBSERVED_DIFFERENT`／`UNKNOWN`。匹配观测不等于状态由本次命令改变，更不证明物理效果。停止或到期撤销临时读与订阅，不撤销已发出的命令。
- 「空调电源：原厂总开关（风向短按）」仅在两分钟验证时加入 `hvac_power` 的订阅和空调组轮询，开始时不会写车。停车后先在原厂面板开关，确认 Dock 风向图标跟随电源状态（关时有斜杠），再短按风向分别试开和试关。以本次会话全局区 `0x80000000` 的有效 `0/1` 回调或读回决定状态，未知不写；只对 `0x10010100` 写裸 `0/1`，不附带写风量、风向、A/C 或 AUTO。图标不按写入返回值提前改变。停止或到期恢复原手势和订阅，不回滚已发出的命令。报告中用 `POWER_WRITE` 区分请求、跳过与实际调用返回，并核对匹配观测和原车界面。
- 2026-11-20 车机日志：临时验证内原车 MAX A/C 出现 3 条有效且区域匹配事件、2 次状态变化，26 次业务读取有效；未见该功能号的 Dock 原生写调用。记录中的 `fast_cool` 是旧组合预设，发的是普通 A/C、手动风量 9 和双区 15.5℃。因此日志不能判定 MAX A/C 写权限、编码或物理效果。
- 基础监听与本次实验订阅合并为同一份按属性集合；ECARX 使用精确 `IFunctionValueWatcher`，GlyCar 使用 `IGlyCarEventCallBack` 与 `registerSingleCarEventCallback`，不退回 GlyCar 全量注册。替换先卸载旧集合，失败不谎报已注册；迟到的旧代理事件被忽略。停止或到期只移除本次实验，恢复原有监听。应用重启不自动恢复实验；native 回调仍可能使普通应用直接闪退，原有熔断保留。
- 验证中的温度组先查询可用性并尝试浮点 ℃ 读取，无效时才走既有整数兜底；10..40℃ 以外、NaN、哨兵和错误 zone 不覆盖已知状态。主副驾按功能号和区域双重匹配。默认运行的温度采样方式不因安装新包而强制改为浮点。
- `HVAC_TEST` 标记区分 START、REGISTER、CAP、READ、EVENT、WRITE、CHECK、END。REGISTER 的 accepted 仅表示注册调用被接受；GlyCar 的 void 门面还会丢弃底层注册返回值，不能据此确认底层接受。CAP 是厂商支持和值域查询，不等于读写授权。报告分别统计实际事件、有效事件、状态变化和真实读取，轮询不会增加事件计数；EVENT 的 delayMs 仅为接收回调到主线程处理的时间，不是车辆操作到显示的总延迟。
- 真车判定：停车后在原车界面改变被测通道的开关或档位，再看对应通道有效且匹配区域的 EVENT 是否增加、值是否随操作变化且 Dock 是否跟随。只有 READ 增加说明轮询可读，不能证明事件订阅可用。需要验证写入时再单独通过 Dock 手动操作；WRITE accepted 只表示接口接受，CHECK_MATCH 是后续同属性同区域真实观测与目标匹配，仍需人工确认物理效果。CHECK_DIFFERENT 是延迟后读回不同；UNKNOWN 是缺少有效证据，均不能一律归因为权限拒绝。
- 查看结果可直接用页面报告并“复制报告”，也可在既有日志中查 `HVAC_TEST`，或只读运行 `adb logcat -s CarDockBar`。诊断沿用本地日志及已有上传策略，不新增上传端点；闪退后应检查上次会话/崩溃证据，不能反复开启导致闪退的通道。不要用 `pm grant` 成功或没有 Java 异常代替真车验证。
- 结束报告的 RESTORE 是旧订阅撤销及基线配置的调用结果；accepted=false 时不能认为已安全撤销，应查看卸载错误，重启应用后不要重复开启故障通道。两分钟期限按单调实时时钟检查，页面切换不结束实验；到期后的旧实验结果不再更新状态。
- 能力查询返回、分组结果应用及已排队事件同时核对验证会话和 Bridge 连接代际；停止重开、保存通道重连或 Binder 重建前的旧结果不能污染新报告或状态。连接变化后按当前基线与实验并集重建选择性订阅；不可抢占的单次厂商调用允许完成，但不再继续旧实验的后续读取。
- 空调写入经 `HvacCommands` 唯一队列执行，所有 Bridge 整数/浮点写入口复核车控 API、写入开关、模拟状态、连接和执行线程，避免组合动作或诊断原始写绕过。未就绪明确返回未执行，不在 UI 线程轮询等待；延迟写后回读也投递同一后台队列。`verifyWrite` 的返回值仅为调用是否接受，UNKNOWN／OBSERVED_MATCH／OBSERVED_DIFFERENT 分开记录，缺失或哨兵读数不再打印“已生效”。

### 1.3 日常同步与目标状态（当前）

- “诊断与日志 → 日常车控状态同步”允许选择风量、AC、主副驾温度、循环、风向和舒适功能。未保存选择时默认订阅手动和 AUTO 风量、AC、循环、风向、主副驾通风及加热、前后挡除霜。前后挡已收到有效且区域匹配的回调，副驾通风尚无实际回调证据；方向盘加热仍默认不勾选。新增默认项不覆盖已保存的配置；原有座椅三路仍只对符合条件的旧配置补入一次，显式全关和熔断清空不补回。日常配置与基线、临时验证取并集，舒适组轮询继续兜底。崩溃证据或早期连续异常仍触发日常通道熔断；稳定后仅有未正常退出标记时保留配置，晚发 native 崩溃与系统杀进程可能无法区分。
- 显式选择日常温度后，温度浮点主动读取不依赖两分钟验证；未选择时保留旧默认读取策略。真实值、显示目标和命令接受分别记录：界面预览不能用作车辆回读，温度持久缓存只保存观测，不保存尚未确认的目标。
- 所有意图在主线程基于当前显示目标累计，再提交不可变目标到共享 worker。尚未执行的独立绝对设温和风量目标可合并；整数步进、双温同步组合、翻转及记忆动作不随意合并。旧序号取消和旧连接结果不得清除新目标，相同显示仍跳过重复绑定。
- 写后确认从实际写动作完成后安排，而不是从主线程提交时刻倒计时。温度定向回读延迟 900ms；仍有效的当前目标按属性续期，不复活过期目标。只有本次真实尝试浮点写入才开启相应温度不超过 3500ms 的浮点确认窗口，默认日常通道空、旧温度监听关闭时也可确认这次业务写入；未确认目标在窗口内使用 500ms 兜底，匹配或到期后恢复常态策略，不把确认变成永久浮点轮询。
- Bridge 的真实写后回读与事件、分组采样归入同一观测状态；应用前核对连接、配置/验证代际和采样版本，旧回读不能覆盖较新的目标或观测。

### 1.4 空调维护边界与操作日志（当前）

- `VehicleController` 保留业务入口、意图/观测归并及分组调度；`HvacWriteActions` 负责单通道、组合、温度兼容等写入策略，不持有显示状态或另建线程；`HvacChannels` 负责纯编码/解码；`VehicleBridge` 仅做厂商反射、能力探测、读写与事件适配。写入和采样继续复用 `HvacCommands` 的唯一 worker，不因拆分增加并行车控队列。
- `HVAC_TRACE` 用 `commandId` 标记用户操作、`wireId` 标记每次真实原生写入；组合动作的每个子写分别记录。QUEUED、SENT、FINISHED 只是操作排队/执行状态；未调用的 SKIPPED 不计为已发送，也不伪造原生耗时。
- NATIVE_PREPARING 只表示调用准备；紧邻原生反射调用激活确认窗口，准备日志和锁等待不算进原生耗时，也不能提前确认。日志分列排队耗时、原生调用耗时、接口返回是否接受及首次合法观测匹配耗时；RAW 调用缺少操作上下文时，排队耗时保留 UNKNOWN。
- 接受与观测彼此独立：accepted=false 不直接推断权限不足；OBSERVED_MATCH、OBSERVED_DIFFERENT、UNKNOWN 均不能证明实际物理效果。首次合法匹配只记录一次，后续外部变化不改写其耗时，超时或旧连接观测不能冒充及时确认。验证报告的业务采样 READ 与原生写后校验分开统计，后者见实际调用流水及 HVAC_VERIFY。

- `HvacChannelEvidence` 会对当前连接的 `VehicleChannels.ALL`、分组读取目录（包括前挡/后挡除霜等舒适通道）及当前订阅回调做有界证据累计；它记录配置/实际 zone、连接与订阅代际、注册接受、事件有效性、轮询变化和读取耗时。未订阅、无事件、坏值或没有现有读取覆盖时只报告 UNKNOWN，不额外探测，也不把注册接受或轮询变化写成事件能力证明。迟到读取仍计真实调用次数，但不覆盖较新的事件基线或增加轮询独有变化计数。

## 2. 车控接口和安全边界

### 2.1 当前默认通道表

以下是 `config/VehicleChannels.kt`、`vehicle/VehicleController.kt`、`vehicle/HvacChannels.kt` 与 `vehicle/HvacWriteActions.kt` 的当前摘要。可配置的通道可在设置页“车控通道”覆盖默认数字；前后挡除霜和方向盘的状态观测沿用下表的固定映射。

| 通道 | functionId | 默认 zone | 当前值域/写法 |
| --- | --- | --- | --- |
| 手动风量 | `0x10020100` | `0x8` | 低字节 0..9，0=关、1..9 档 |
| AUTO 风量 | `0x10020200` | `0x8` | 实际映射：1→`0x10020204`、2→`01`、3→`02`、4→`03`、5→`05` |
| AUTO 总开关 | `0x10010200` | `0x80000000` | 裸值 0/1，裸值优先 |
| 温度（主驾/副驾） | `0x10060100` | 1 / 4 | 目标范围15.5..28.5℃，默认浮点绝对目标；显式关闭浮点写时保留整数兼容，不自动跨类型/区域试写 |
| 双温同步 | `0x10060500` | `0x80000000` | 0/1 |
| AC | `0x10010300` | `0x80000000` | 日常明确编码裸值0/1，未知/哨兵不当真实关闭 |
| 风向 | `0x10070100` | `0x8` | `func + 1..7`，位掩码语义尚未逐项实车确认 |
| 内外循环 | `0x10030100` | `0x80000000` | 外循环裸值 0，内循环复合 `0x10030101` |
| 前挡除霜 | `0x10040200` | `0x80000000` | `writeSwitch`，复合值优先、裸值兜底 |
| 后挡除霜 | `0x10040300` | `0x80000000` | `writeSwitch`，复合值优先、裸值兜底 |
| 主/副驾座椅通风 | `0x10050100` | 1 / 4 | 裸值 `0` 关闭，`func + 1..3` 开启 |
| 主/副驾座椅加热 | `0x10050200` | 1 / 4 | 裸值 `0` 关闭，`func + 1..3` 开启 |
| 方向盘加热 | `0x10090100` | 状态读取及事件匹配 `0x80000000`；写入默认 `1` | 0..3 档，不是简单布尔开关 |

重要纠偏：

- AUTO 使用专用 `0x10020200` 通道和乱序映射，编码以 `HvacChannels.kt` 为准；历史“01…05 顺序映射”或“手动风量写 10”的说明不能覆盖当前执行逻辑。
- 内外循环的旧 zone `0x8` 是已确认的错误配置；当前默认全局 zone 为 `0x80000000`。
- `Prefs.tempCustomizeWriteEnabled` 默认true，常用设温和步进均先计算绝对目标后走已有GlyCar/Customize浮点写；整数兼容需显式选择，步进逐条执行，不合并、不在升温失败后尝试降温。旧整数绝对值按round(℃/0.2)编码；supported values里的[2]不解释为温度范围，接口接受不等于真车效果。
- 旧文档中“开关统一为 10/11”是某次外部设备/历史日志的层级编码，不应替代当前 `HvacChannels`、`HvacWriteActions` 和 `VehicleChannels` 的实际值域。

### 2.2 车控读写机制总览（当前）

- **统一底层链路**：读取和写入都通过 `VehicleBridge` 的反射适配访问厂商 `ICarFunction`/GlyCar 接口；业务状态由 `VehicleController` 归并。业务写入和常态分组读取主要复用 `HvacCommands` 单一后台 worker 串行执行；诊断页的独立只读查询使用自己的后台线程，不在 UI 线程等待车控调用。
- **常态调度**：`DockOverlayService` 每 250ms 只检查刷新期限；实际读取由 `VehicleRefreshQueue` 分组排队，分组完成后重新计算下一次期限。基础周期为：风量 500ms、AC/循环/风向/双温同步 1000ms、温度 2500ms、座椅/除霜/方向盘加热等舒适通道 2500ms、点火和环境传感器 2500ms。周期是调度间隔，不是严格 UI 延迟上限；厂商 IPC 耗时和共享队列排队会叠加。
- **事件订阅默认值**：手动风量、AUTO 风量、AC、内外循环、风向及主驾通风、主副驾加热。升级只补入旧配置缺少的座椅选项，保留显式全关和熔断；双温同步仍随 CLIMATE 组订阅，温度仍由原有温度监听默认订阅，旧 `vehicle_watcher_enabled` 全量开关仍默认关闭。
- **风量**：手动和 AUTO 风量属于 FAN 组，分别使用专用 functionId 和编码；当前默认常态事件订阅，因此车辆风量变化优先由事件更新，FAN 轮询作为兜底。AUTO 模式切换是同一后台操作中的 AUTO 总开关与 AUTO/手动风量写入组合。
- **AC、循环、风向和双温同步**：属于 CLIMATE 组。双温同步的真实值由 `0x10060500` 的合法读回或事件归并，弹窗不再使用本地偏好作为最终状态；未收到完整合法事件时继续按 1000ms 基础周期读取，四项均出现合法事件后才按 2500ms 兜底。循环和风向的车型值域/语义仍以实际观测和真车证据为准。
- **主副驾温度**：属于 TEMPERATURE 组，默认保留温度事件监听；浮点主动读取只在日常温度配置、临时 TEMPERATURE 验证或有限写后确认窗口内启用。常规温度写入默认走 Customize/GlyCar 浮点绝对目标，显式关闭浮点写入才走整数兼容；写后确认从真实写动作完成后安排，不把目标值直接当车辆回读。
- **座椅、除霜、方向盘加热**：属于 COMFORT 组。默认订阅主驾通风、主副驾加热；其余四路可按需加入。回调按功能号和区域匹配，订阅不改变舒适组的轮询周期。座椅非零档位默认直接写目标通道；关闭用裸值 `0`，同侧两项独立处理，ECarX 明确报告副驾通风不可用时跳过该写入。前后挡除霜为开关，方向盘加热为 0..3 档，原写入行为不变。
- **舒适功能显示**：在 `COMFORT` 后台队列独立查询支持状态。座椅通风按两侧各自配置的功能号与区域查询（默认 `0x10050100`、1／4），方向盘按原厂全局区查询 `0x10090100`（不改变现有写入区）。只将明确的 `notavailable` 用于隐藏；单参数查询不能判断主／副驾，档位 0、`notactive`、未知和异常也不作为隐藏依据。断连、模拟或关闭车控时撤销旧能力判断；能力查询不随弹窗 500ms 档位轮询加速。
- **传感器**：点火、挡位、手刹、日夜模式和 PM2.5 等事件型传感器通过 `getSensorEvent` 拉取；车内/车外温度等连续量通过 `getSensorLatestValue` 拉取。它们不是 HVAC functionId 事件订阅，也不写入车控。
- **写入确认语义**：写入返回 `accepted` 只表示厂商方法接受；后续真实事件或读回分别记录 `OBSERVED_MATCH`、`OBSERVED_DIFFERENT` 或 `UNKNOWN`。任何一种代码结果都不能单独证明车辆物理效果，需结合原车显示或真车观察。

- 座椅验证模式只在用户显式启动的两分钟窗口内生效，不改变日常默认写入路径；GlyCar 路径不可用时会在日志中记录无会话或无方法，不自动伪造成功。
- 车机取证（2026-11-19，DCY11）：ECarX 直写已实测能开启及换档；组合模式当时因相反模式的关闭调用返回 `false` 未发送目标，GlyCar 无会话、未发送整型写。日常保留直写，不自动切换到其它路径；`HVAC_TEST SEAT_WRITE` 与 `HVAC_TRACE`、`HVAC_VERIFY` 或 `HVAC_VERIFY_GLYCAR` 分开记录发出的值、调用接受及实际回读。修改后关闭及常态订阅的真车效果仍需回归。

### 2.3 写入保护

- `HvacCommands`与Bridge在提交及实际写入前统一检查API、模拟状态、写开关、连接和worker线程。日常写仅使用明确编码与配置zone；未逐车型验证的舒适/整数兼容最多尝试同区两种表示，不跨区域盲写，也不因调用返回true就持久化修改zone。
- `HvacWriteActions.writeSwitch` 先调用 `VehicleBridge.supportOf`，再依 `bareFirst` 选择裸值或复合值优先，并通过 `verifyWrite` 和延迟回读记录结果。
- `VehicleBridge.writeInt` 会先探测支持状态；不支持或异常要记录权限拒绝/非法值，不得盲写。厂商 HAL 对不支持的 `(functionId, zone, value)` 可能触发 native abort，Java 层不能靠 try/catch 兜底。
- 温度回读的边界伪值和 `0xfd`、`0xfe`、`0xff` 等无效哨兵不能覆盖真实观测；显示目标只在有限期限内保留，未获有效确认时回落最近真实值，不将目标当回读，也不自动重写。
- `verifyWrite` 的返回值只是当前写调用是否返回成功，真实观测另记 OBSERVED_MATCH／OBSERVED_DIFFERENT／UNKNOWN；不能因为方法名含“verify”就把 `true` 写成“真车已生效”，也不能把某些通道的 `false` 一律解释为被拒绝。
- 车控初始化和写入受崩溃熔断开关控制。不要把“熔断后暂时只读”误写成车控问题已修复。

### 2.4 连接、升级和验证

- 车控通过反射适配厂商接口，编译期不依赖厂商 jar；普通应用不能直接获得 oneOS 系统应用的 platform 权限。
- `App.kt` 的 `preserveUiUpgrade` 只匹配旧版本非空且版本字符串以 `3.13.105(` 到 `3.13.112(` 或 `4.0(` 开头的升级。它不是“所有升级都保留一切”的泛化策略。
- 未命中保留分支时，版本变更会重置 crash streak、safe level、车控写入/API/温度 watcher 开关，并记录新版本；命中分支则只更新 lastVersion，保留现有开关和安全等级。后续修改版本兼容逻辑时必须重新核对这段可执行条件。
- 当前代码、模拟器和逻辑测试不能代替真实车型回归；车控写入、车型信号、系统权限和数值语义均需日志或真车证据。
- `VehicleClient.kt`、`VehicleControlService.kt` 保留了独立 `:car` 进程的实验性客户端/服务实现，但当前 Manifest 未注册该服务、当前调用点也直接使用 `VehicleController`；不要把这组文件写成当前已启用的 native 崩溃隔离边界。

## 3. 启动核心权限检查与补齐

- 当前车机目标环境为 Android 9 / API 28；`App.kt` 在应用初始化后调用 `util/StartupPermissions.kt` 后台检查。核心授权是运行必需项，每次启动及现有恢复入口均会补齐缺项，不提供自动补权开关，也不区分用户手动撤销或系统关闭。旧版关闭自动补权的配置不再生效；“检查并补齐权限”可显式重新检查。
- 必需范围为悬浮窗、通知使用权、前台检测无障碍及维护所需的 `WRITE_SECURE_SETTINGS`，不受 Dock、歌词、媒体开关或安全等级影响。业务服务的启停仍遵守这些开关和熔断。Android 9 不执行 `POST_NOTIFICATIONS` 或 `MANAGE_EXTERNAL_STORAGE` 命令；通知发送权限只在 Android 13+ 的版本守卫内处理。
- 另对本应用声明的四项车控权限 `CONTROL_CAR_CLIMATE`、`CAR_ENERGY`、`CAR_INFO`、`CAR_EXTERIOR_ENVIRONMENT` 检查缺项；设备存在相应定义时尝试 `pm grant` 并最终回读，已授予的不重复申请。标准 Android 9 的 `CONTROL_CAR_CLIMATE` 定义为 `system|signature`，普通 shell 可能被拒绝；不能由“拿到 shell”或旧注释推断所有车型均能授权，不绕过签名/安装身份校验。
- 普通声明权限已授予时不重复申请；存储、系统日志、未知来源安装和电池白名单不在自动清单中。补权不写车控通道，也不改变安全等级、媒体开关或车控熔断。
- ADB 仅连接现有本机 adbd，优先读取设备当前/持久化 TCP 端口并使用统一候选列表；不开放端口、不关闭认证、不调用 `su`。所有可检查的核心与车控授权已满足时不建立 ADB 会话；命令被拒绝或最终回读未授予时明确报告，不伪称已开启。
- `AdbClient` 使用旧协议字节累加校验、严格会话校验和整体期限；命令只有正常结束并取得退出码 0 才算执行成功。原始输出和界面“无输出”文案分离，最终授权仍需 Android API/设置回读；无障碍名单合并时保留其它服务，名单存在不等于服务已连接。
- 单次命令输出上限为 1 MiB；日志或包信息采集不完整时明确报告原因和片段，不据此生成“没有相关日志”的结论。内外循环取证先在设备端按同一组固定关键词过滤，减少无关日志占用传输容量；`getevent` 按期限读取片段的既有用途保留。
- 授权变化后复用现有 Dock 重载、媒体重绑和歌词启动入口，保持用户原有启停状态。授权未变化时不因重复检查重建已运行的窗口，媒体仅刷新；缺失的业务服务仍按原开关恢复，不通过重启应用替代恢复。代码及本机协议/模拟运行验证不能替代本车机授权和实际窗口、媒体、无障碍连接验证。

## 4. 诊断、日志和崩溃排查

### 4.1 当前上传行为

`LogUploader` 的默认端点解码后为：

```text
https://28059b4b3e6a450db00a72ad75ea95a0.sg2.agentos-app.run/upload
```

当前默认开启上传；用户在设置页填写的有效 endpoint 优先于默认值，空值及已知历史死链会在启动迁移时纠正。网络可用时自动上传，失败会进入本地队列并在网络恢复或下次上传动作时补发；不能承诺任何网络环境下都即时成功。

上传类型包括：

- `live`：约 1.5 秒或累计约 40 行批量上传。
- `crash`：Java 未捕获异常和日志尾部。
- `prev_session`：下次启动补传上次会话日志，覆盖 native 崩溃无法触发 Java 回调的情况。
- `diag`：车控后端、方法签名、温度通道和首帧原始值。
- `manual`：设置页手动快照。

单条 payload 上限当前为 22,000 字符，超长内容保留头尾；失败队列包括 `files/logs/live_queue.txt` 和 `files/logs/pending.jsonl`。

### 4.2 本地日志文件和服务

应用私有目录的关键文件：

- `files/logs/session.log`
- `files/logs/prev.log`
- `files/logs/native_crash.txt`、`native_crash.txt.err`
- `files/last_crash.txt`
- 诊断页“导出诊断与运行日志”通过 Android 系统创建文档保存器生成 ZIP，由用户选择保存位置，不申请存储权限、不自动上传。ZIP 包含固定白名单中的 `session.log`、`prev.log`、native/abort 证据、最近 Java 崩溃归档、`HvacDiagnostics` 和 `HvacChannelEvidence` 报告、内存日志补充及 UTF-8 元数据；缺失文件明确列出。
- 导出副本会过滤运行日志中的 URL 查询凭据和 Authorization bearer 内容；不包含 SharedPreferences、上传队列、密钥或其他应用私有文件。日志可能包含应用名、包名、媒体和车控诊断信息，分享前需由用户自行确认接收者。保存器取消、启动失败或写入失败均不报告成功，临时文件在结束时清理。

根目录 `log_server.py` 是纯 Python 标准库的局域网接收服务，默认监听 `0.0.0.0:8080`，按天写入 `log_server_logs/YYYY-MM-DD.jsonl`。它只适用于开发诊断，不是 CI 发布服务。远程服务端的子域名可能因重新部署变化；修改默认端点后必须重新核对代码并重新构建。

常用只读诊断示例（不得借此操作用户设备）：

```bash
adb -s <serial> logcat -s CarDockBar
adb -s <serial> shell run-as com.car.dockbar ls files/logs/
adb -s <serial> shell run-as com.car.dockbar cat files/logs/session.log
```
远程接收端源码在 `log_upload_service/server.py`，只依赖 Python 标准库，提供 `/health`、`/logs` 和 `/download`。`/logs` 默认返回最近 200 条，可用 `limit`（上限 5000）和 `app` 筛选。`date=YYYY-MM-DD` 会包括该日基础文件及其分片；`date=YYYY-MM-DD.2` 可选相应分片前缀。排查全天时不要只读一个分片，远程域名是否仍可用需实际检查，本文不声称已拉取在线日志。


### 4.3 崩溃降级

- App 启动时先轮转上次会话、收集崩溃证据并尝试补传，再开始当前会话的实时日志。
- 上一次运行少于约 15 秒并发生崩溃会增加 streak；连续崩溃会逐级关闭高风险能力，当前阶梯封顶 L3。
- 车控写入熔断后仍可保留读取；“多次闪退后又能启动”可能只是熔断生效，不能直接说明根因消失。
- 版本变更的重置行为以 `App.kt` 当前代码为准，不要照抄旧 Handoff 中“所有升级都会重置”或“所有升级都会保留”的单一说法。

### 4.4 音量日常同步

- Dock 服务运行时监听 `android.media.VOLUME_CHANGED_ACTION`，媒体流 3 定向回读更新 Dock 媒体图标；音量弹窗显示时也按通知回读对应的导航（流 15）、电话（流 0）、语音（流 11）。不采用广播携带的音量、不触发写入；同路在途通知合并，服务退出撤销监听并忽略迟到结果。
- 保留主栏 2500ms 媒体采样与音量弹窗 500ms 轮询。广播不送达、注册失败或回读无效时依赖轮询，不需开启两分钟验证。
- 2026-11-20 的 `VOLUME_TEST` 记录：媒体流 3 的 7 次广播均有有效且一致的回读，7 次均确认变化；其它三路没有对应变化证据，不能由这份日志判定支持或不支持。接收至回读的耗时不是操作到显示的总延迟。

## 5. 未验证事项和交付边界

以下项目不能仅通过文档整理标为完成：

1. 真车上前挡/后挡、方向盘加热、座椅记忆是否真正生效。
2. 当前车型 `0x10060100` 浮点温度路径、上下限信号和整数回退的实际响应。
3. 风向 1..7 每个组合对应的真实出风方向。
4. 座椅 0..3 每档的实际强度语义。
5. AQI/车内外温度信号的车型值域。
6. 歌词悬浮窗在所有播放器和车型上的兼容性。
7. Android 特殊权限是否因重启、刷机或系统策略被撤销。

验证时必须区分：

- 源码/单元测试证据：能证明代码路径和纯逻辑。
- 模拟器证据：能证明 UI 或无车环境交互，不能证明真实车辆。
- 车机日志证据：能证明某次设备上的调用、返回和回读。
- 真车回归证据：才能确认车型上的实际车控效果。
